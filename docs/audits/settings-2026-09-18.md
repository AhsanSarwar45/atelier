# What the settings screen actually does, 2026-09-18

Every control on the Claude Code and Codex settings screens was driven in a
real browser against an instance built from this worktree, and the file each
control writes was read back afterwards. This is what was found (bw-6ecp.1).

## How it was driven

A headless Chromium, through the project's own Playwright, against an isolated
instance on port 3101: its own `XDG_DATA_HOME`, `ATELIER_DATA_DIR`,
`CLAUDE_CONFIG_DIR` and `CODEX_HOME`, none of them the owner's. Two Claude
accounts, `system` and `work`, the second added through the Accounts screen
during the run.

For each setting the driver read the control's current value, set it to a
different one, read the provider's file to confirm the write landed, then
reloaded the page and read the control back.

## The round trip is sound

| Page | Settings | Wrote and read back |
|---|---|---|
| Claude, Defaults | 19 | 19 |
| Claude, Permissions | 14 | 14 |
| Codex, Defaults | 25 | 25 |
| Codex, Approvals and sandbox | 8 | 8 |

No console errors and no uncaught exceptions on any settings section. The
other sections — Appearance, Notifications, Accounts, Agent files, Search,
Terminal, Dependencies, Tags — were opened and exercised too. Theme, interface
font size, the notification switches, the search selects and the terminal shell
all persist across a reload, and the terminal shell's refusal of a path that is
not there is printed word for word.

So "the setting does not save" is not what is wrong. What is wrong is that
some of what is saved is not what the provider accepts, and that a value can be
destroyed without being asked about.

## What is wrong

### The value written is one the provider rejects

`sandbox.allowUnsandboxedCommands` is offered as a choice between "Retry" and
"Forbid" and writes the string `"retry"` or `"forbid"`. Claude Code documents
this key as a boolean, default `true`. Neither string is a value it accepts, so
the setting does nothing whatever the reader picks.
Source: https://code.claude.com/docs/en/settings-reference#sandbox-allowunsandboxedcommands

### Models that no longer exist are offered

Codex's model list offers `gpt-5.4` and `gpt-5.4-mini`, both retired from Codex
on 2026-08-31, and `gpt-5.5`, which retires on 2026-10-14. Picking one writes a
model Codex will not run.
Source: https://learn.chatgpt.com/docs/models

### Two permission modes are offered where they cannot take effect

`permissions.defaultMode` offers `auto` and `bypassPermissions` on the project
screen as well as the account screen. Claude Code honours those two only from
the user settings file, `--settings` or managed settings — from a project or
local file they are silently ignored, and the screen says nothing about it.
Source: https://code.claude.com/docs/en/permission-modes

### One malformed line empties the whole setting

The environment-variable control, and Codex's `shell_environment_policy.set`,
take `NAME=value` a line at a time. A line with no `=` is dropped without a
word, and if no line has one the key is written as an empty object — so a typo
on one line discards every variable that was already there. Driving it with two
lines that had no `=` left `"env": {}` in the file.
`src/components/settings/provider-settings-panel.tsx`, `LinesControl`.

### A ceiling the provider does not have

"Keep transcripts for" refuses anything over 3650 days. Claude Code documents a
minimum of 1 and no maximum; the ceiling was invented here.
Source: https://code.claude.com/docs/en/settings-reference#cleanupperioddays

### A shape the control cannot hold

Codex's `approval_policy` also accepts a table — `{ granular = { ... } }`. The
screen draws it as a choice of two strings, so a config that uses the table form
reads as unset here, and writing the control replaces the table with a string.
Source: https://learn.chatgpt.com/docs/config-file/config-reference

### A group description that contradicts the reference

The Codex sandbox group says `default_permissions` is "ignored when a profile is
set". The reference says not to combine `default_permissions` with
`sandbox_mode` or `[sandbox_workspace_write]` at all — it is a conflict, not an
override.
Source: https://learn.chatgpt.com/docs/config-file/config-reference

### Skills do not follow the account

Every other row of the Agent files screen reads from the chosen account's own
directory. Codex's personal Skills row reads `$HOME/.agents/skills`, so every
account shows the same skills, and an instance pointed at another home still
lists the owner's. `server/src/workbench/agent_files.rs:280`.

### An MCP server belongs to one account and nothing says so

`~/.claude.json` is read for the System account only, and only when
`CLAUDE_CONFIG_DIR` was unset when the server started
(`server/src/workbench/registry.rs:382`). Every other account reads its own
`.claude.json`. A chat is launched with `CLAUDE_CONFIG_DIR` pointed at the
account's directory and no MCP configuration passed through
(`server/src/workbench/acp/adapter.rs:153`), so the agent loads whatever that
directory holds.

Driven: with two servers under System, the MCP tab for System lists
`codegraph` and `vercel`, and the tab for `work` says "None". That is the
manager's chrome-devtools report — the server is in `~/.claude.json`, the panel
shows it under System, and an agent on another account cannot see it. Nothing on
the screen explains the split or offers to copy a server across.

The provider's own documentation names this trap: relocating the config
directory orphans the user-scope MCP servers.
Source: https://code.claude.com/docs/en/claude-directory

### The add form is drawn in the section's header

The add-server form is placed in the section header's action slot, so at a
phone width it is a box floating in the upper right with the "MCP servers"
heading beside it rather than a form the reader fills in. The same is true of
adding a plugin and adding a marketplace. It is not a popup — its position is
`static` — which is why it neither dims the page nor closes on Escape.

### Copy to... copies one page, and does not ask which

The button copies only the tab that happens to be open — the dialog is headed
"Copy defaults to" — and for every key of that page it writes the source's
value or, where the source has none, a deletion. So it can clear settings in
the target that were never shown to the reader. Driven: `work` had
`language: German` and `editorMode: vim`; copying Defaults from System replaced
both without warning. MCP servers and plugins cannot be copied at all.
`src/components/settings/copy-to-accounts.tsx:32-53`.

### The Copy to... button shares a row with the account picker

At every phone width measured (360, 384, 390, 412, 430 CSS px, and at interface
font sizes up to 22px) the button is not clipped — it keeps a 16px margin. But
it sits on one line with an account picker that takes the rest of the width,
and its label is the elided "Copy to...", which is why it reads as cramped.
`src/components/settings/provider-section.tsx:103-106`.

## What was checked and found sound

`fallbackModel` really is an array, and `attribution.commit` and
`attribution.pr` really are strings that hide the line when empty — all three
were suspected and all three are right. Every other key on both providers'
pages exists, at that dotted path, with the type the schema gives it, and every
other choice list matches the provider's accepted values.
